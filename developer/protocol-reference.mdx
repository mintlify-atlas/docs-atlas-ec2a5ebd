---
title: "Native stub JSON protocol reference"
description: "Complete reference for the JSON messages exchanged between the awawausb browser extension and the native stub binary over stdin/stdout."
---

The extension background script and the native stub binary communicate using the standard [native messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging) format: each message is a length-prefixed JSON object sent over stdin/stdout. Every message carries a `"type"` field that identifies its variant. Binary data (USB payloads) is encoded as base64url without padding.

## Common fields

Two fields appear in nearly every message:

- **`sid`** — Session ID (string). An opaque identifier assigned by the native stub that represents a specific USB device. Sent with `NewDevice` responses and must be echoed back in all device-scoped requests.
- **`txn_id`** — Transaction ID (string). Formatted as `"pageID-txnID"`. The browser sets this on every request; the native stub echoes it back in the corresponding `RequestComplete` or `RequestError` response so the extension can match responses to outstanding requests.

    <ResponseField name="product" type="string">

    ### RequestComplete

    Sent when a non-isochronous request completes successfully.

    <ResponseField name="type" type="string" required>

    </ResponseField>
    <ResponseField name="txn_id" type="string" required>

      `true` if the device sent more data than the requested `length` (babble condition).
    </ResponseField>
    <ResponseField name="data" type="string">
      Data received from the device for IN transfers, base64url encoded without padding. Absent for OUT transfers.
    </ResponseField>
    <ResponseField name="bytes_written" type="number" required>
      Number of bytes written to the device for OUT transfers (`u64`). Zero for IN transfers.
    </ResponseField>

    ---

    ### RequestError

    Sent when a request fails.

    <ResponseField name="type" type="string" required>
      Always `"RequestError"`.
    </ResponseField>
    <ResponseField name="txn_id" type="string" required>
      Transaction ID from the originating request.
    </ResponseField>
    <ResponseField name="error" type="string" required>
      One of the error code strings from the `Errors` enum. See [Error codes](#error-codes) below.
    </ResponseField>
    <ResponseField name="bytes_written" type="number" required>
      Number of bytes written before the error occurred (`u64`). May be non-zero for partial writes.
    </ResponseField>

    ---

    ### IsocRequestComplete

    Sent when an isochronous request completes. Each packet has an individual status entry.

    <ResponseField name="type" type="string" required>
      Always `"IsocRequestComplete"`.
    </ResponseField>
    <ResponseField name="txn_id" type="string" required>
      Transaction ID from the originating request.
    </ResponseField>
    <ResponseField name="data" type="string">
      Data received for IN isochronous transfers, base64url encoded without padding. Absent for OUT transfers.
    </ResponseField>
    <ResponseField name="pkt_status" type="string[]" required>
      Per-packet status array. Each element is one of `"Ok"`, `"Babble"`, or `"Error"`. The length matches the number of packets in the original request.
    </ResponseField>
    <ResponseField name="pkt_len" type="number[]" required>
      Actual number of bytes transferred for each packet (`u32[]`).
    </ResponseField>

## Error codes

These values appear in the `"error"` field of a `RequestError` message.

| Code | Meaning |
|---|---|
| `DeviceNotFound` | The device ID is bogus, or the device was surprise-removed between the request being sent and processed. |
| `RequestTooBig` | The request exceeds a platform limit — e.g. a control transfer larger than `0xffff` bytes, or an isochronous transfer with too many packets. Platform-specific quirks are not hidden. |
| `Stall` | The device returned a USB STALL condition on the endpoint. |
| `TransferError` | An unspecified transfer error occurred. |
| `InvalidState` | The requested operation cannot be performed in the current state — e.g. attempting a transfer on a device that has not been opened, or on an interface that has not been claimed. |
| `InvalidNumber` | The specified interface or endpoint number is not valid for this device. |
| `AlreadyClaimed` | The requested interface is already claimed (by this session or another). |

## Example exchange

The following shows a complete `OpenDevice` request followed by a successful `RequestComplete` response.

```json
// Browser → native stub
{
  "type": "OpenDevice",
  "sid": "abc123",
  "txn_id": "42-1"
}
```

```json
// Native stub → browser
{
  "type": "RequestComplete",
  "txn_id": "42-1",
  "babble": false,
  "data": null,
  "bytes_written": 0
}
```

A control IN transfer (device-to-host) and its response:

```json
// Browser → native stub
{
  "type": "ControlTransfer",
  "sid": "abc123",
  "txn_id": "42-2",
  "request_type": 128,
  "request": 6,
  "value": 256,
  "index": 0,
  "length": 18
}
```

```json
// Native stub → browser
{
  "type": "RequestComplete",
  "txn_id": "42-2",
  "babble": false,
  "data": "BBAGAAAAAQIDBA",
  "bytes_written": 0
}
```
